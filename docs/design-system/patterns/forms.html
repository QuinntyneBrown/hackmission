Forms

How forms are laid out, when they validate, and what they say.

PatternComposes form-field, text-field, button

Overview

Forms on the site are small: the signup (one field), the unsubscribe confirmation (two buttons). Organiser forms will be longer. The rules are the same: label every control, validate on submit then live, keep the typed value on failure, say what happens next on success.

When to use which

SituationUse
One field + one actionInline row (.signup__row)
Up to ~8 fieldsSingle column, 36rem
Short related pairs (first/last name)Two columns ≥ 768px
Destructive confirmationDialog or simple page with safe action first
Long multi-stepStepper pages, one step per page

The signup, invalid: error first, help second, value kept, focus on the field.
  • Label above the control (visually hidden only when the context makes it obvious).
  • Error before help in the DOM so it is read next.
  • Actions bar: safe action first, primary last.

States

  • Validation timing: on submit; then live as the person fixes the field (not while they first type).
  • Submitting: form aria-busy, button busy + disabled, fields read-only; typical response < 1 s.
  • Server error: inline alert above the field, value kept, danger toast too.
  • Success: form replaced in place by the result card; focus moves to it; what happens next is stated.
  • Already subscribed: a success-like result, no error.

Responsive behaviour

  • Inline rows stack below 640px.
  • Two columns collapse below 768px.
  • Primary action full width on phones.

Accessibility

  • novalidate with custom messages; aria-invalid + aria-describedby.
  • Error summary (role="alert", focused) when more than one field can fail.
  • Required stated in words; autocomplete on every known field (3.3.7, 1.3.5).
  • No cognitive tests (3.3.8).

Content

  • Help: what the value is used for.
  • Errors: how to fix it.
  • Success: what happens next, with the email shown back.
